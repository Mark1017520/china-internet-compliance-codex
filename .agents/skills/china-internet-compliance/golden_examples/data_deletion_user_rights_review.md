# Golden Example — Data Deletion User Rights Review

## 1. 输入事实摘要

App 计划新增账号注销功能。用户提交注销后，产品只隐藏前端账号，订单、客服记录、营销标签、设备标识和第三方推送 SDK 数据仍保留。客服说明“用户一般不会追问”，未设计删除/匿名化范围、留存例外、完成通知和第三方同步删除。

## 2. 结论前置

- 风险等级：P1 高风险
- 上线建议：明确账号注销后的删除、匿名化、必要留存和第三方同步删除规则后再上线
- 核心理由：仅前端隐藏账号不能满足用户删除/注销预期。订单、客服、营销标签和第三方 SDK 数据需要按目的、法定留存和最小必要分别处理并留痕。

## 3. 事实矩阵

| 事实项 | 内容 | 状态 |
|---|---|---|
| 用户动作 | 账号注销 | 高关注 |
| 当前处理 | 前端隐藏账号 | 不充分 |
| 保留数据 | 订单、客服、标签、设备标识、SDK 数据 | 高关注 |
| 留存例外 | 未说明 | 缺失 |
| 第三方同步 | 未设计 | 缺失 |
| 完成通知 | 未设计 | 缺失 |

## 4. 主要问题

| 问题 | 等级 | 触发事实 | 关闭标准 |
|---|---|---|---|
| 删除范围不清 | P1 | 多系统仍保留个人信息 | 输出系统级删除/匿名化清单 |
| 法定留存和业务留存混同 | P1 | 订单和客服记录全部保留 | 区分必须留存、可匿名化和应删除字段 |
| 第三方同步删除缺失 | P1 | 推送 SDK 等仍保留 | 向第三方发送删除/停止处理请求并留痕 |
| 用户权利响应不足 | P1 | 未通知完成结果 | 提供进度、完成通知和申诉入口 |
| 恢复和撤销规则不明 | P2 | 注销后可能恢复 | 明确冷静期、撤销和不可恢复边界 |

## 5. 整改建议与责任方

| 整改项 | 责任方 | Gate |
|---|---|---|
| 制作系统级个人信息清单和注销处理矩阵 | 数据/研发/隐私 | 上线前 |
| 区分删除、匿名化、法定留存和争议留存字段 | 法务/隐私 | 上线前 |
| 建立第三方同步删除、停止处理和证明留档机制 | 研发/采购/隐私 | 上线前 |
| 用户侧展示注销影响、处理期限、完成通知和申诉入口 | 产品/客服 | 上线前 |
| 对删除任务建立日志、失败重试和定期抽检 | 研发/安全 | 灰度前 |

## 6. 上线 Gate

未完成跨系统删除矩阵和第三方同步删除机制前，不建议上线账号注销。若存在法定留存，应在用户告知中明确保留目的、范围和期限，不得以“内部需要”笼统保留。

## 7. 依据状态

- 待核验依据：个人信息删除、更正、账号注销、法定留存和第三方处理相关规则需核验最新版官方文本。
- 内部规则/风险偏好：用户权利请求应纳入客服和隐私工单闭环。

## 8. 可复制评审结论

【结论】当前账号注销只隐藏前端账号，不满足删除和停止处理的合规预期。建议按 P1 处理，补齐系统级删除/匿名化矩阵、法定留存例外、第三方同步删除、完成通知和日志抽检后再上线。
